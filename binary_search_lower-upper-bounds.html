Chapter 01

What are bounds?

A sorted array can hold duplicate values. Classical binary search finds some occurrence of a target — but often you need to know exactly where a value's range begins and ends. That's what bounds give you.

LOWER_BOUND

First valid position

The index of the first element ≥ target. The leftmost position where you could insert the target and keep the array sorted.

UPPER_BOUND

First position past the target

The index of the first element > target. One past the last occurrence — the rightmost valid insertion point.

Key relationship: for any sorted array, upper_bound(x) − lower_bound(x) gives the exact count of occurrences of x. If this equals 0, the element doesn't exist.

Chapter 02

The pseudocode

All three algorithms — exact binary search, lower bound, and upper bound — share the same skeleton. The differences are small but have large consequences. Start with exact binary search as the baseline, then see exactly what changes.

exact_search(arr, target) — the baseline pseudocode 
function exact_search(arr, target):
    lo = 0
    hi = len(arr) - 1   // ① hi is the LAST valid index, not one past end

    while lo <= hi:    // ② loop condition includes equality (lo == hi is still valid)
        mid = (lo + hi) // 2

        if arr[mid] == target:   // ③ FOUND — return immediately
            return mid
        elif arr[mid] < target:
            lo = mid + 1
        else:
            hi = mid - 1   // ④ hi shrinks by mid-1, not mid

    return -1            // ⑤ not found → -1 (no "ans" variable needed)
Five structural differences — exact search vs bounds
①
hi = len(arr) - 1 in exact search  vs  hi = len(arr) in bounds. Bounds use a half-open interval [lo, hi) so hi can represent "one past the last element" as a valid answer (meaning: not found, or insert at end).
②
while lo <= hi in exact search  vs  while lo < hi in bounds. Because bounds use an exclusive hi, the interval is empty when lo == hi, so the loop exits there.
③
return mid immediately on == in exact search  vs  no early return in bounds. Bounds never stop on a match — they record ans = mid and keep narrowing to find the first or last occurrence.
④
hi = mid - 1 in exact search  vs  hi = mid in bounds. In bounds, when mid is a valid candidate we set hi = mid (not mid-1) to preserve mid in the search window — otherwise we could skip the answer.
⑤
returns -1 on miss in exact search  vs  returns len(arr) on miss in bounds. A bound result is always a valid insertion index; -1 would be meaningless as a position.
lower_bound(arr, target) pseudocode 
function lower_bound(arr, target):
    lo  = 0
    hi  = len(arr)     // ① one past end (not len-1)
    ans = hi           // ⑤ default answer: not found

    while lo < hi:    // ② strict less-than (not <=)
        mid = (lo + hi) // 2

        if arr[mid] < target:    // two branches only — no == branch  ③
            lo = mid + 1
        else:                     // arr[mid] >= target: candidate found
            ans = mid            // ③ record but do NOT return yet
            hi  = mid            // ④ hi = mid, not mid-1

    return ans           // first index where arr[i] >= target
upper_bound(arr, target) pseudocode 
function upper_bound(arr, target):
    lo  = 0
    hi  = len(arr)     // ① one past end
    ans = hi

    while lo < hi:    // ② strict less-than
        mid = (lo + hi) // 2

        if arr[mid] <= target:   // only change vs lower_bound: <= instead of <
            lo = mid + 1         // equal values are also discarded — push right
        else:                     // arr[mid] > target: candidate found
            ans = mid            // ③ record but do NOT return
            hi  = mid            // ④ hi = mid, not mid-1

    return ans           // first index where arr[i] > target

Why bounds use hi = mid instead of hi = mid - 1: when a bound finds a candidate at mid, it can't discard mid the way exact search does. It must preserve it — just narrow the window so it can check whether something earlier (or later) is also valid. Setting hi = mid - 1 would skip the answer entirely.

C++ STL — using the standard library

In practice you never write the loop yourself. The C++ standard library ships both functions in <algorithm>. They return an iterator — dereference it with * to get the value, or subtract v.begin() to get the index.

std::lower_bound — C++ STL c++ 
#include <algorithm>
#include <iostream>
#include <vector>
using namespace std;

int main()
{
    // Sorted vector
    vector<int> v = {10, 20, 30, 40, 50};

    // Finding lower bound of 30
    cout << *lower_bound(v.begin(), v.end(), 30);
    // Output: 30  (iterator points to first element >= 30)

    return 0;
}
std::upper_bound — C++ STL c++ 
// C++ Program to illustrate use of std::upper_bound() for vector
#include <algorithm>
#include <iostream>
#include <vector>
using namespace std;

int main()
{
    // Sorted vector
    vector<int> v = {10, 20, 30, 40, 50};

    // Finding upper bound of 30
    cout << *upper_bound(v.begin(), v.end(), 30);

    return 0;
}

Reading the condition

When arr[mid] < target is true: mid is definitively too small. Every element at or before mid is also too small. We set lo = mid + 1, discarding the entire left half including mid.

When arr[mid] < target is false (i.e., arr[mid] ≥ target): mid is a valid candidate. We record it in ans and set hi = mid to search leftward — there may be an earlier occurrence.

Reading the condition

When arr[mid] <= target is true: mid is at or below the target. Even if arr[mid] == target, we don't stop — we need the first position strictly after all equal values. We set lo = mid + 1.

When arr[mid] <= target is false (i.e., arr[mid] > target): mid is a valid candidate for the upper bound. We record it and search left for an even earlier one.
